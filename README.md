# Персонализированный AI-ассистент утреннего экрана

**sain-hack-2026-team16 | Кейс №1**

Интеллектуальный сервис для анализа пользовательских привычек за 90 дней и динамической генерации персонализированного утреннего дашборда.

Система объединяет глубокий анализ поведенческих паттернов с генеративным пользовательским интерфейсом (подмножество **A2UI**), подбирая релевантные виджеты и формируя ответы с учетом контекста, календаря и целей пользователя.

**Репозиторий:** [TheBettterFlower/sain-hack-2026-team16](https://github.com/TheBettterFlower/sain-hack-2026-team16)

## Ключевые возможности

- **Долгосрочная память (90 дней):** анализ истории событий пользователя за последние три месяца, выявление устойчивых закономерностей, трендов и смены привычек.
- **Динамический UI (A2UI):** автоматический подбор от 1 до 4 наиболее актуальных виджетов для утреннего приветствия на основе расписания в календаре и текущих целей.
- **Каталог из 12 виджетов:** проработанная библиотека UI-компонентов (от `sleep_card` до `restart_card`) с дружелюбным UX-копирайтингом без нравоучений.
- **Оптимизация производительности:** потребление RAM строго ≤ 512 МБ (за счет SQLite в `/tmp`), ответ сервера укладывается в лимит 45 минут.

## 1. Запуск проекта

### 1.1. Запуск на боевом стенде хакатона

Деплой на стенд автоматизирован через GitHub Actions.

1. Убедитесь, что в репозитории настроен секрет `STAND_SSH_KEY`.
2. Сделайте push в ветку `main`.
3. Файл `.github/workflows/deploy.yml` автоматически отправит код на стенд.
4. Стенд развернет контейнер, установит пакеты из `requirements.txt` и запустит сервер командой из `start.sh`:

```bash
exec uvicorn main:app --host 0.0.0.0 --port "${PORT:-8000}"
```

### 1.2. Локальный запуск

Для локальной разработки предусмотрен режим с Mock-данными, позволяющий тестировать приложение без расходования лимита запросов к LLM.

**Шаг 1. Клонирование репозитория**

```bash
git clone https://github.com/TheBettterFlower/sain-hack-2026-team16.git
cd sain-hack-2026-team16
```

**Шаг 2. Создание виртуального окружения**

```bash
python -m venv venv
```

Активация окружения:

```bash
# Linux / macOS
source venv/bin/activate

# Windows
venv\Scripts\activate
```

Установка зависимостей:

```bash
pip install -r requirements.txt
```

**Шаг 3. Настройка переменных окружения**

Для использования Mock-данных установите режим разработки:

```bash
# Linux / macOS
export ENV=dev
export LLM_API_KEY=dev-key
```

**Шаг 4. Запуск бэкенда**

```bash
bash start.sh
```

**Шаг 5. Запуск фронтенда**

Откройте второй терминал и выполните:

```bash
cd sain-hack-2026-team16/frontend
npm install
npm run dev
```

После запуска фронтенда откройте локальный адрес, указанный Vite в терминале.

## 5. Журнал технических решений

### 5.1. Хранение данных пользователя (ограничение памяти)

**Проблема:**

Изначально рассматривался вариант загрузки JSON и хранения всех словарей за 90 дней в оперативной памяти (в списках Python).

**Почему отказались:**

При размере датасета в десятки мегабайт такой подход мог быстро превысить установленный лимит в 512 МБ ОЗУ на контейнер.

**Принятое решение:**

Использовали SQLite с хранением базы данных в `/tmp/hackathon.db`.

Это позволило:

- Выполнять эффективные выборки.
- Делегировать агрегацию привычек движку БД через `GROUP BY`.
- Снизить потребление оперативной памяти.

### 5.2. Ограничение токенов (300 000 в сутки)

**Проблема:**

Первоначально рассматривалась отправка каждого вопроса из массива `questions` в `gpt-6-luna` отдельным запросом.

**Почему отказались:**

Скрытые токены рассуждения модели (400–500 на вызов) быстро расходовали суточный лимит.

**Принятое решение:**

Реализовали батчинг:

- Группируем вопросы по 20 штук.
- Отправляем их единым массивом.
- Сокращаем количество запросов и экономим десятки тысяч токенов.

### 5.3. Обработка ошибки 429 Too Many Requests

**Проблема:**

Изначально рассматривалось использование линейной задержки (`time.sleep(5)`) при получении ошибки превышения RPM-лимита.

**Почему отказались:**

При высокой нагрузке на прокси организаторов запросы продолжали отклоняться, что могло нарушить выполнение всего процесса `/run`.

**Принятое решение:**

Внедрили алгоритм **Exponential Backoff**.

При возникновении ошибки сервер последовательно увеличивает время ожидания: 2, 4, 8 секунд и далее.

Это повышает устойчивость системы к временным ограничениям API.

### 5.4. Запуск веб-сервера

**Проблема:**

Первоначально рассматривался запуск приложения через Gunicorn.

**Почему отказались:**

Воркеры Gunicorn по умолчанию могут завершаться по таймауту в 30 секунд, тогда как обработка всего `/run` может занимать до 45 минут.

**Принятое решение:**

Перешли на чистый Uvicorn, который используется для запуска приложения и обработки длительных запросов.

### 5.5. Тестирование клиентской части (Frontend)

**Проблема:**

Первоначально рассматривалось тестирование фронтенда с отправкой запросов к реальной нейросети на боевой стенд.

**Почему отказались:**

Существовал риск исчерпать лимит в 300 000 токенов за несколько дней до онлайн-проверки.

**Принятое решение:**

Ввели переключатель `IS_DEV` в бэкенде.

В режиме разработки сервер возвращает статический Mock-JSON, позволяя фронтенд-разработчику безопасно разрабатывать и тестировать компоненты без обращения к реальной нейросети.

## 6. Архитектура проекта

Проект состоит из двух основных частей:

### Backend

- FastAPI — серверная часть приложения.
- SQLite — хранение и обработка пользовательских данных.
- LLM — анализ поведенческих паттернов и генерация персонализированных ответов.
- API — взаимодействие с сервисом хакатона.

### Frontend

- React — клиентская часть приложения.
- A2UI — декларативное описание динамического интерфейса.
- Каталог из 12 виджетов — компоненты утреннего дашборда.
- Механизм динамической сборки экрана на основе JSON, полученного от бэкенда.

### Основной сценарий работы

1. Получение пользовательских данных через API хакатона.
2. Сохранение и обработка истории событий за 90 дней.
3. Анализ привычек и поведенческих паттернов с помощью LLM.
4. Выбор от 1 до 4 наиболее релевантных виджетов.
5. Формирование JSON-описания интерфейса.
6. Динамическая отрисовка персонализированного утреннего экрана на React.
